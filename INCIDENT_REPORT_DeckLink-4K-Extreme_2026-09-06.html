1. Executive Summary

On September 6, 2026, at 02:28:23 UTC, an SDI live recording session on device DeckLink 4K Extreme ran for 47 minutes and 54 seconds. Upon stopping the recording, the StreamOps UI flagged the recording status as:

UI Status Banner: "This capture is incomplete. The file contains 00:14:17 of playable media from a 00:47:54 recording session; preview and download can only include media actually written to disk."

A complete diagnostic investigation was conducted across Docker container logs, kernel ring buffers (dmesg), disk I/O metrics, and FFmpeg telemetry. Conclusion: The system did not crash, Linux kernel OOM killer was not triggered, and disk capacity was not exhausted (355 GB free).

The incident was caused by an I/O write throughput bottleneck resulting from selecting Uncompressed 10-bit Video (v210) in QuickTime MOV simultaneously with MPEG-2 MXF. The uncompressed video stream demanded 1.11 Gbps (~138 MB/sec) of sustained disk write speed. This saturated host I/O, lowered encode speed below real-time (0.93x), caused massive DeckLink hardware input buffer overruns, choked the MPEG-2 muxing queue at 00:14:17, and rendered the 353 GB MOV file unreadable without its trailing moov atom.

3. Technical Root Cause Analysis (Deep Dive)

A. Uncompressed 10-bit Video (`v210`) Bandwidth Demands

When uncompressed SDI recording is selected, video is captured frame-by-frame with zero compression:

Format Profile Resolution & Rate Bitrate Sustained Throughput 1-Hour Storage Demand
Uncompressed 10-bit (v210) 1920×1080 @ 25i 1,105,920 kbps ~138.2 MB/s ~497.6 GB / hour
XDCAM Broadcast Master (MPEG-2) 1920×1080 @ 25i 50,000 kbps ~6.25 MB/s ~22.5 GB / hour

Standard cloud storage volumes, single SATA/NVMe drives, or Docker volume mounts cannot sustain 140+ MB/s random writes while simultaneously reading and transcoding video without hardware buffer overruns.

C. Why the Missing Media (14:17 to 47:54) Cannot Be Recovered

  1. Hardware Drop: The Blackmagic DeckLink card transfers uncompressed live SDI in real-time. When the buffer filled, incoming camera frames were discarded at the PCIe driver layer. The unwritten frames were never encoded and do not exist on disk.
  2. Purged MOV File: The 353 GB MOV file lacked a moov atom (file header index). Even if carved from unallocated disk space, it consists of raw unindexed v210 blocks, many of which have already been overwritten by subsequent recording sessions (04-48-28.mxf, 05-49-02.mxf, 07-15-32.mxf).

4. Corrective & Preventative Actions (SOP)

System Operational Status: The server hardware and DeckLink card are completely healthy. The subsequent session DeckLink-4K-Extreme_2026-09-06_04-48-28.mxf completed flawlessly.

To prevent recurrence, the following Standard Operating Procedures (SOP) must be enforced:

  1. Restrict Uncompressed Ingest:
    Do NOT select v210 (Uncompressed QuickTime MOV) on standard storage volumes. Uncompressed capture should only be permitted if a dedicated NVMe RAID-0 storage tier (>1,200 MB/s sustained write) is mounted.
  2. Standardize on Broadcast Presets:
    For broadcast delivery and editing, use standard broadcast profiles:
    • Standard Broadcast Master: MPEG-2 / XDCAM HD422 @ 50 Mbps (.mxf) — ~6.25 MB/s (Recommended).
    • Web & Archive Master: H.264 / AVC MP4 @ 15-25 Mbps (.mp4) — ~2.5 MB/s.
    • Editing Master: Apple ProRes 422 (.mov) — ~18.5 MB/s.
  3. Single Format Export Policy:
    During live SDI capture, do not simultaneously select multiple master encoding profiles unless high-speed multi-disk storage is explicitly verified.
